## 结论与证据规则

目标是 **R7F701381 / RH850/P1M-E**。P1M、P1M-E、P1x-C、U2A6 的资料不能因系列名称接近而互换；MCAL 包名或 OS variant 为 P1M，也不能证明其所有寄存器都适用于 P1M-E。

| 优先事项 | 本次答案 | agent 应如何使用 |
| --- | --- | --- |
| Code Flash | 1 MB，原 `2048K` 假设错误 | 以 1 MB 用户区审核链接布局；不要把系列最大容量当本型号容量 |
| CAN 时钟 | 接口 pclk=80 MHz；位时间源为 40 MHz 或 16 MHz | 先确定 DCS，再计算分频；不要用 80 MHz 算 BRP |
| CAN mask | 硬件 0 不比较、1 比较 | 追踪 MCAL 生成转换，不能直接把配置 mask 改成硬件值 |
| OSTM | 0/1 可用于普通 EI 中断；3～7 是 FEINT | 分配资源时区分中断级别；Gpt 已用 OSTM0 是截图信息 |
| TickCounter | 优先解释 OSTM1 自由运行硬件路线 | 保留连续时间基准，处理回绕、晚匹配、取消和并发 |
| 板级/工具专属值 | 当前未知 | 明确需要查哪个文件、字段或板卡网名，不补造数值 |

本文使用三种证据标签：**手册确认**（适用型号的文档事实）、**推导/建议**（基于事实的计算或方案）、**未知**（依赖未提供的工程、板卡或工具版本）。手册确认不等于实物测量。下文 DS-E、HW-E 等编号均在资料索引定义；页码为已提取 PDF 的页码。

## A. 芯片与时钟

<a id="A1"></a>
### A1：型号、内核、FPU 与编译目标

**手册确认：** R7F701381 属 P1M-E，G3M 主核带检查核锁步，具有双精度 FPU；100 引脚 LFQFP、14×14 mm、DPS。检查核不是第二个可独立运行任务的应用核。来源：DS-E pp.1–3。

**回答：** `-cpu=rh850g3m` 的内核选择与硬件一致；不能仅凭存在 FPU 就删除 `-fsoft`。是否使用软件浮点还取决于 GHS 版本、编译和链接选项、运行库、RTAOS.a/MCAL ABI，以及 OS 对浮点上下文的保存策略。完整订货后缀仍未知。后续 agent 应读取构建命令和库说明，确认全工程浮点调用约定一致；不能只改一个源文件的选项。

<a id="A2"></a>
### A2：内存容量与链接布局

**手册确认：** Code Flash 用户区 1 MB：`0x00000000–0x000FFFFF`；Data Flash 32 KB：`0xFF200000–0xFF207FFF`；LRAM 128 KB：`0xFEDE0000–0xFEDFFFFF`；GRAM 两个 32 KB bank：`0xFEEF8000–0xFEEFFFFF`、`0xFEF00000–0xFEF07FFF`。LRAM 的 PE1 别名不是额外 RAM。另有 32 KB Code Flash 扩展用户区，不能自动并入从零开始的连续 iROM。来源：DS-E pp.2–3，HW-E pp.257–258。

**回答：** 原 `iROM 2048K@0x0` 应按目标型号收紧为 1024 KB；若有 bootloader、保留区，还需进一步分区。`PLRAM 118K@0xFEDE0000` 与 `stack 10K@0xFEDFD800` 的区间衔接正确，栈上界为 `0xFEE00000`（不含）。这不证明栈足够，也不证明 `.data/.bss` 没有占用保留区。后续检查 map 的 VMA/LMA、段大小、栈边界和别名重复分配。

<a id="A3"></a>
### A3：晶振、PLL、总线与外设时钟

**手册确认：** MainOSC=16 MHz，CPU=160 MHz，HSB=80 MHz，LSB=40 MHz，内部 IOSC=8 MHz；WDTA 选 8 MHz 或 250 kHz。OSTM0/1 可直接按 PCLK 计数，也可选择 TAUD/TAUJ 计数使能链。CAN 位时间见 A4。来源：HW-E pp.469–471、791、1534、1547–1560。

**回答：** 目标手册的时钟图是 MainOSC→PLL→CPU/HSB/LSB，不能把其他芯片的 `PLL0/PLL1` 配置项直接当本器件寄存器。`App_MCU_P1M-E_701381_Sample.arxml` 仅有文件名，尚无内容，故无法给出真实工程的逐字段差异。内部 agent 应建立“ARXML 参数→生成值→时钟选择/分频寄存器→输出频率”的链，尤其分清时钟监测、外部 CLKOUT 配置与 CPU 主时钟。板上晶振实值仍未知。

<a id="A4"></a>
### A4：500k/1000k CAN FD 位时间

**手册确认及推导：** GCFG.DCS=0 选 40 MHz clkc，DCS=1 选 16 MHz clk_xincan；80 MHz pclk 是接口时钟。公式为 `bitrate=fCAN/(divider×(1+TSEG1+TSEG2))`。来源：HW-E pp.791、921–922、935–936、949、1092。

| 条件 | 标称阶段（divider/TSEG1/TSEG2/SJW） | 数据阶段 | 采样点 |
| --- | --- | --- | --- |
| 40 MHz 参考候选 | 2 / 31 / 8 / 4 → 500k | 2 / 15 / 4 / 3 → 1000k | 均 80% |
| 16 MHz 参考候选 | 2 / 12 / 3 / 2 → 500k | 2 / 5 / 2 / 1 → 1000k | 81.25% / 75% |

40 MHz 候选 FD 接口寄存器为 NCFG=`0x071E1801`、DCFG=`0x023E0001`。物理 divider=2 对应 BRP 编码 1；不要把物理 Tq 数和减一编码混用。两阶段 NBRP/DBRP 须相同；启用 TDC 时分频也受约束。

截图的数据 SJW=4 与 TSEG2=4 满足寄存器文字的非严格关系，但手册图 p.1092 使用严格不等式；案例暂取 SJW=3，同时保留该文档差异，不能断言原值必然无效。候选仍需与网络传播延迟、收发器及 MCAL 参数定义配套。位时间函数和主机测试见参考代码。

## B. 中断

<a id="B1"></a>
### B1：直接向量还是表参考

**回答：两种机制均有，当前工程选择未知。** EIC.EITB 决定相应 EI 通道采用直接分支或表参考。表参考读取地址是 `INTBP+4×EI通道号`，该位置存放 handler 地址；它不是处理函数本体地址。直接分支依据 RBASE/EBASE、PSW.EBV、RINT 和优先级选择入口，不能用 `4×通道` 替代。来源：HW-E pp.267–268、281–290。agent 应联查 EITB、INTBP、向量 section 和 OS 生成入口。

<a id="B2"></a>
### B2：所需外设的中断表

**手册确认：** 完整的 EI 通道、表偏移、EIC 地址已列在 [硬件报告第 4 节](hardware-findings.md#4-中断映射)：WDTA0=9，OSTM0/1=74/75，TAUJ0 四通道=133～136，CAN0 error/common(Tx/Rx) FIFO receive/Tx=183/184/185（EI184 **不是** Rx FIFO 中断），CAN 全局 error/Rx FIFO0–7=189/190，Flash end/error=379/383。EIC 为 16 位，EIP 为 4 位、复位 15。

OSTM3～7 共用 FEINT 路径，不能分配普通 EI EIC 地址；该目标没有 OSTM2 或 WDTA1。出处：HW-E pp.267–268、282–290、792、1544。注意“表偏移”与 B3 的 ETAS 名字不是同一字段。

<a id="B3"></a>
### B3：Interrupt_0228/022C 与 ISR 名字

**硬件确认：** OSTM0/1 的 EI 通道是 74/75，INTBP 表偏移为 `0x128/0x12C`，EIC 是 `0xFFFFB094/0xFFFFB096`。**未知：** RH850GHS 5.0.39 如何把这些通道命名为 `Interrupt_XXXX`。

**回答：** 截图的 `0228/022C` 与 `4×通道` 相差 `0x100`，但这只是可检查的数值关系，不足以宣布命名规则是 `0x100+4n`。不要擅自重命名成 `0128/012C`。正确取证链为端口 device/interrupt 定义→生成的 `Os_ConfigInterrupts.h`→ISR ARXML→向量表/链接 map；每个源填写一行。三个 CAN ISR 也要分别追踪源，不能按数量猜测覆盖范围。ETAS 5.0.39 官方安装包入口已找到但下载需登录，尚未取得端口内容，见网上参考资源。

<a id="B4"></a>
### B4：EIP 与 OsIsrPriority/IPL

**手册确认：** EIP=0～15，0 最高、15 最低；同级待处理中断的硬件选择还涉及通道固定优先级。来源：HW-E pp.268、281。

**回答：** `OsIsrPriority/IPL_x` 到 EIP 的映射是 OS 端口契约，不能直接令其相等，也不能未经确认套用 `15-x`。应从端口枚举/生成表找到一项优先级的编码，再核对对应 EIC 写入。Cat1/Cat2 和 OS 屏蔽级也一并核对；CPU 的硬件优先级结论不能代替 OS 可调用服务的规则。

## C. OSTM

<a id="C1"></a>
### C1：寄存器、位定义与访问宽度

**手册确认：** OSTM0=`0xFFDD8000`，OSTM1=`0xFFDD9000`；OSTM3～7 从 `0xFFD70000` 起，步长 `0x40`。下表适用于所列 OSTM 寄存器；TO/TOE 输出功能仅 0/1 有效。来源：HW-E pp.1543、1551–1556。

| 寄存器 | 偏移 / 宽度 | 语义 |
| --- | --- | --- |
| CMP | +0x00 / 32 | 比较值，读写 |
| CNT | +0x04 / 32 | 当前计数，只读 |
| TO | +0x08 / 8 | bit0 输出电平 |
| TOE | +0x0C / 8 | bit0：0 软件控制 TO，1 中断时翻转输出 |
| TE | +0x10 / 8 | bit0：1 计数启用，只读 |
| TS | +0x14 / 8 | 写 bit0=1 启动；不能靠读 TS 判断状态 |
| TT | +0x18 / 8 | 写 bit0=1 停止 |
| CTL | +0x20 / 8 | bit1 MD1：0 间隔向下/1 自由向上；bit0 MD0：启动时是否请求中断 |

CTL 只在 TE=0 时可改；未实现位按手册保留值写入。停止后 CNT 保留，但自由运行重新启动会从 0 开始。参考代码使用正确宽度；并未实现所有外设或 ISR 语义。

<a id="C2"></a>
### C2：哪种模式支持自由计数和匹配，晚匹配怎么办

**回答：** 使用 MD1=1 的自由运行比较模式。间隔模式从 CMP 向下计数，适合周期通知，不能直接作为保持连续原点的上计数器。写入已过去的 CMP 不能指望马上补发事件。EIRF 对同步边沿源允许软件置位，这是构造补发路径的硬件条件；必须核实目标源类型和 OS 对到期请求的契约。来源：HW-E pp.267、1562、1567。

**建议：** 保存本次目标和代次，在受保护区内装载 CMP 并重新读取时间；发现目标已到期则安排一个有效请求，避免等到下一圈；使用单一分发路径防止硬件匹配与软件补发重复处理。不能用未约束距离的有符号差直接判断任意 32 位远期匹配。完整设计见 [K1](counter-design.md)。

<a id="C3"></a>
### C3：读取、设置、取消、清挂起与状态

**回答：** CNT 用 32 位读取；CMP 用 32 位写入。EIMK=1 只屏蔽 CPU 接收，不阻止 EIRF 继续形成；EIRF 的写入权限随请求类型变化。EIC 读改写有丢失或重复请求风险，不能对整个 16 位寄存器随意 `|=`/`&=`。来源：HW-E pp.267–268、1552–1556。

取消的是本次 alarm 请求，不是自由运行的时间基准。建议内部维护 `armed/deadline/generation`，按目标源的规程撤销/隔离待处理请求，并让 ISR 拒绝旧代次；重新 Set 前清理由旧目标造成的残留。仅屏蔽 EIMK、仅清一次 EIRF、或调用 Ostm_Stop 都不能单独证明满足 Cancel。State 返回哪些字段必须来自端口头文件，不把自定义 bool 作为真实返回类型。

<a id="C4"></a>
### C4：32 位硬件计数换算为 16 位 1 ms tick

**推导：** 计数频率为 f 时，每 tick 的 counts 为 f/1000。80 MHz 下为 80000，20 MHz 下为 20000。OS 模数是 65536，周期 65.536 s；80 MHz 原始计数的回绕周期仅 53.6870912 s。

因此 `((CNT/80000)&0xFFFF)` 错误：在硬件回绕时丢失了历史时间。案例采用无符号相邻差累计，并保留不足 1 ms 的余数，要求采样间隔严格小于一圈、访问串行化且计数器不被重置。该算法通过 100000 次采样测试，但维护采样周期仍属于集成责任。长 alarm 的 CMP 安排也需维护分段；不能把 65.535 s 的目标直接截成 32 位 count。见 counter-design.md。

<a id="C5"></a>
### C5：OSTM1 是否空闲，是否存在核/时钟限制

**回答：** 硬件有 OSTM1，且可走 EI75；这不证明工程中空闲。截图已说 OSTM0 被 Gpt 使用，应先把 OSTM0 视为已占用。内部 agent 可以把 OSTM1 列为首选候选，但必须查 Gpt 配置、OS timer、启动代码、测试驱动和直接 MMIO 访问，建立唯一所有者表。HW-E pp.1542–1544；G3M 锁步检查核不用于分配第二份 OSTM 驱动。守护/访问权限和外部启动信号也属于初始化前提。

<a id="C6"></a>
### C6：CK0、2.0E7 与实际计数时钟

**回答：** `2.0E7` 表示配置声称 20 MHz，`CK0` 只是选择名；它们不证明计数器真的以 20 MHz 运行。IC0CKSEL0/1 位于 `0xFFDD6000/0xFFDD6004`，16 位访问；bit15=0 直接选 PCLK，bit15=1 使用 bit13:12 指定 TAUD0/TAUD1/TAUJ0/TAUJ1，再由对应字段选通道。还要沿该通道找到 CK0～CK3 及预分频。来源：HW-E pp.1547–1560。

若实际 PCLK=80 MHz，却按 20 MHz 给间隔比较值 19999，则重复周期约 0.25 ms，不是 1 ms。确认 20 MHz 后重复周期 CMP=19999；80 MHz 则 CMP=79999。首个启动周期另按手册时序处理。已有 Ostm_InitPclk 会选择 PCLK，不能悄悄替换现有 CK0 初始化。

## D. CAN 与收发器

<a id="D1"></a>
### D1：实际 CAN 通道、引脚和 ALT

**手册确认：** 100 引脚 DPS 的 CAN0 RX 候选 P3_7/P2_0/P4_5，TX P3_8/P2_1/P4_6；CAN1 RX P3_12/P2_2/P4_2，TX P3_13/P2_3/P4_3；CAN2 RX P5_6、TX P5_5。来源：DS-E p.23。

**回答：** 板上所用组合未知；不能从这些候选任挑一对当实际配置。先由原理图收发器 TXD/RXD 回溯 MCU 管脚，再查对应端口的复用表得到 ALT 和方向，最后核对 Port 生成值。旧 P1x 的 CAN2 TX=P5_7 不可沿用。ALT 的原理见 I2，不能跨封装抄选项。

<a id="D2"></a>
### D2：STB/EN/ERR/WAKE 与开机时序

**回答：未知的是板卡接线和收发器语义，不是 MCU 手册中的缺省值。** U2A6 的 STB1/EN1 只可保留逻辑信号名，不可复制 port/bit、有效电平或延时。读取原理图/BOM/收发器手册，记录每个信号的方向、上拉下拉、复位时电平、使能真值表和稳定时间。

建议解说顺序：先建立不误发报文的输出锁存电平→配置 GPIO/复用→按收发器要求供电和切换模式→等待规定稳定条件→允许控制器通信。此处不指定毫秒延时，也不把 EN 高、STB 低视为所有器件通用规律。

<a id="D3"></a>
### D3：13 个邮箱、7 个过滤规则、16 字节与轮询

**回答：** MCAL 的 HOH/邮箱是软件配置对象，不等于 13 个连续硬件 buffer。需要展开每项的 controller、方向、hardware object、FIFO、rule index、payload allocation。已知七个十进制 ID 对应如下，均在 11 位范围内，但帧格式仍要查配置。

| 十进制 | 十六进制 |
| --- | --- |
| 1248 | 0x4E0 |
| 2015 | 0x7DF |
| 20 | 0x014 |
| 253 | 0x0FD |
| 1010 | 0x3F2 |
| 1264 | 0x4F0 |
| 123 | 0x07B |

硬件 GAFLIDM 为 1 的位参与比较、0 的位不比较；标准 ID 精确匹配需要有效 ID 位全部参与，并按需求约束 IDE/RTR。配置 `mask=0` 是否反相要读生成器，不能仅据参数名判错。HW-E p.968。

CAN FD 普通 Tx buffer 可容纳至 20 字节，merge 扩到 64 字节；16 字节本身在普通模式容量以内，但仍需校验分配和 DLC，经典 CAN 不能发 16 字节帧。Padding 值未知，不填默认值；非直接可编码长度如何补齐也应遵守所用 MCAL API。两阶段 BRP 相同的约束见 A4。来源：HW-E pp.789、922、1078、1092。

轮询不等于所有 CAN 中断都应关闭。为 Rx、Tx confirmation、bus-off、error 分别指定唯一服务入口及调用周期，避免轮询和 ISR 双重消费同一事件；当前三个 ISR 的职责仍需 B3 的映射证据。

<a id="D4"></a>
### D4：是否需要睡眠、唤醒和 EcuM 配置

**回答：** 现有需求不足以断言“需要”或“不需要”。本解说的最小通信案例采用保持唤醒的正常收发；把低功耗作为条件分支说明。若业务需要总线唤醒，则核查收发器唤醒输出/能力、MCU 唤醒源、CAN 控制器模式转换、EcuM source ID、验证/清除逻辑和复位后状态。若无相关要求，记录“不在当前功能范围”，不要伪造已通过唤醒测试。

## E. Flash、Fee 与 NvM

<a id="E1"></a>
### E1：Data Flash 容量、粒度与寿命

**手册确认：** 32 KB，范围 `0xFF200000–0xFF207FFF`，64 B 擦除块（512 块），4 B 编程操作规格。DS-E p.63 在平均 Ta=85°C 条件下给出 125000 次/20 年保持或 250000 次/3 年保持。来源另见 HW-E pp.257、2859。

**回答：** Fls 配置必须以 32 KB 型号边界为准，不能沿用 64 KB 系列成员。4 B 规格不等于任何时候都可对任意 4 B 连续重写；实际命令序列、对齐、空白检查、ECC 与重复编程限制仍按 Flash Hardware Interface 手册和所用库约束。擦除态的普通读取不能未经确认就当稳定 0xFF；应优先使用硬件/库规定的 blank-check 流程。

<a id="E2"></a>
### E2：Fls/Fee FS1x/NvM 与 RAM 执行

**回答：** Data Flash 支持后台操作期间从 Code Flash 执行（HW-E pp.2857、2869），因此不能一概要求整个 Fls 驱动搬到 RAM；Code Flash 自编程、厂商 Flash 库的特定例程及读同一忙资源的限制要另查。

agent 的检查链：Fls sector 起止/粒度→保留空间与 Fee 虚拟扇区→NvM block 长度/管理开销→异步 MainFunction 和通知→重启恢复。FS1x 名称本身不能证明已适配本器件；应查 Fee 的底层需求、Fls API/作业结果、擦除值假设和配置版本。

若库明确要求 RAM 例程，则须同时有 Flash 装载地址、RAM 执行地址、复制表、启动搬运、调用目标和必要的常量数据，而不是仅声明 MemMap 宏。查 map 和引用链确认 ISR/常量不会访问正在操作的受限 Flash 区。现有 Fls_Cfg、MemMap 与 linker 内容未知，故只能给出此审核方法，不能声称它们已经正确。

<a id="E3"></a>
### E3：外部 EEPROM/Flash

**回答：板上有无及型号均未知。** MCU 集成 Data Flash 既不能证明没有外部存储，也不能证明必须有。由 BOM、原理图中的 SPI/CSIH/CSIG 等连接和 Eep/Ea/外部 Fls 配置交叉确认；没有外部器件证据时，参考案例仅解释片内 Data Flash 路径，不编造器件列表。

## F. 看门狗

<a id="F1"></a>
### F1：WDTA0 地址、默认启动与首次期限

**手册确认：** WDTA0 基址 `0xFFD74000`；OPWDRUN=0 软件触发启动，=1 复位释放后启动；OPWDMDS=0 为 8 MHz，=1 为 250 kHz。初始 OVF 来自 option，周期 `2^(9+OVF)/WDTATCKI`，OVF=0～7。来源：HW-E pp.1522、1531、1534–1535、2884。

**推导：** 8 MHz 下可选名义周期 64 μs～8.192 ms；250 kHz 下 2.048～262.144 ms。默认启动时，启动代码必须在实际首周期内触发，并留出振荡器容差/执行延迟余量。具体期限取决于板上 OPBT0，不能直接给出固定 1 s。WDTAnMD 只能在首次触发前按手册更改一次；后续不能任意动态改硬件模式。

<a id="F2"></a>
### F2：SetTriggerCondition(1000) 的含义

**回答：** AUTOSAR 的该参数表示驱动触发条件的毫秒时间额度，不是把 WDTA 硬件单次溢出周期改成 1000 ms。驱动可以在额度有效期间按更短的合法窗口周期喂硬件；额度到期后停止触发。公开的 [AUTOSAR Watchdog Driver R23-11 §8.3.3](https://www.autosar.org/fileadmin/standards/R23-11/CP/AUTOSAR_CP_SWS_WatchdogDriver.pdf)明确了毫秒换算语义；本项目 4.2.2/厂商实现仍需对应版本核对，不能以新规范替代其全部行为。

判断 1000 是否合理需同时读取 WdgMaxTimeout、模式、驱动服务周期、窗口约束、应用/WdgM 更新周期以及启动触发安排。仅看到该函数调用不能宣布合理或错误。尤其不能每次定时中断都无条件延长额度，从而掩盖应用停止运行。

<a id="F3"></a>
### F3：WDG_59_DRIVERA_TRIGGERFUNCTION_CAT2_ISR 来源

**手册确认：** WDTA0 有 75% 中断，EI9，表偏移 0x24，EIC=`0xFFFEEA12`；MD.WIE 控制请求使能。来源：HW-E pp.282、1531。

**回答：** 名为 TRIGGERFUNCTION 的 Cat2 ISR 可能承担驱动喂狗服务，但名字不能证明中断源。只有当 ARXML/生成向量把它映射到 EI9，且驱动启用 WDTA 75% 事件时，才能认定该绑定。也要排查是否实际由其他 timer 驱动。75% 中断不是复位事件，不能混淆两者。

## G. GHS 启动、复位和内存

<a id="G1"></a>
### G1：reset.850/crt0 的职责和顺序

**建议的依赖顺序：** 复位入口及最早异常保护→确认复位原因/上电 WDTA 期限→确保将使用的 RAM/ECC 已有效→设置可用栈与编译器所需基址→完成规定的 `.data` 搬运和 `.bss` 初始化→完成所需时钟/外设初始化→建立 OS 向量与 ISR 上下文→启动 OS 和应用。早期使用 C 函数之前，其栈、数据和 ABI 前提必须成立；若硬件已初始化 RAM，不要又无条件清空保留区。

这是一份依赖解说，不是未经核验的 GHS 汇编脚本。`sp/gp/ep/tp` 必须绑定本工具版本的链接符号与模型，不从 CC-RH 示例复制寄存器初始化。来源：HW-E pp.257、281、2890；编译器差异见 [Renesas CC-RH 启动示例](https://tool-support.renesas.com/autoupdate/support/onlinehelp/csp/V8.15.00/CS%2B.chm/Compiler-CCRH.chm/Output/ccrh08c0300y.html)。

<a id="G2"></a>
### G2：GHS 参数是否适合

**回答：不能仅根据芯片型号批准整组选项。** 以下为审核重点，不冒充已查到的本地 GHS 版本定义：

| 截图参数 | 要核对的内容 |
| --- | --- |
| `-large_sda -sda=0` | 组合的有效含义、选项顺序/覆盖规则、是否实际生成 small-data 引用及链接符号 |
| `-registermode=32` | 所用 OS/运行库的寄存器约定和上下文保存集合 |
| `-reserve_r2` | 编译器、OS 与手写汇编对 r2 的保留和使用是否一致 |
| `-no_callt` | 生成代码、预编译库、启动代码是否对 CALLT 表有一致要求 |
| `-fsoft` | 浮点代码生成/调用约定、运行库与上下文策略，见 A1 |

实际做法是收集所有编译单元和库的有效选项，检查 startup 设置的基址与 map 定义，反汇编关键调用检查引用。当前没有 GHS 对应版本文档，故不臆测 `tp` 的寄存器编号或提供可执行启动命令。

<a id="G3"></a>
### G3：FENMI、FEINT、SYSERR、TRAP 与 MCAL 入口

**手册确认：** FENMI 固定偏移 +0xE0，FEINT +0xF0；它们与 EIINT 表参考机制不同。HW-E p.281 提醒 FENMI、FEINT、直接向量 EIINT、SYSERR、FPI 的入口同步要求（SYNCP），详细规则应联查 G3M 软件手册和端口入口代码。来源：HW-E pp.281–282。

**回答：** SYSERR/TRAP 的准确入口、基址选择和返回协议应由 G3M 软件手册及现用 OS/启动实现确定，本次没有把其他内核的常见偏移当作已确认值。`MCU_FENMI_ENTRY` 是工程宏，不能证明 MCAL 提供了函数实现。追踪宏展开→符号定义→链接落点→实际异常 wrapper；禁止用普通 C 函数直接替代需要保存上下文的入口，也不要让“链接成功”掩盖默认死循环入口。

<a id="G4"></a>
### G4：PLRAM 清零、ECC、PORST/TRAPRST 段

**手册确认：** 本器件对 LRAM/GRAM 等有硬件初始化/ECC 机制，各类复位行为受配置控制。来源：HW-E p.2890。

**回答：** 先查复位种类、硬件初始化模式和完成条件，确保首次读取/压栈前 ECC 有效；需要软件初始化时按手册允许宽度和范围执行。`.bss.PORST.*`、`.bss.TRAPRST.*` 只是工程命名，无法从名称确定哪些复位清零、哪些保留。按链接归属和启动清零表解释；保留数据还需要有效性标记，不能在一次清零时同时销毁待分析的复位日志。

<a id="G5"></a>
### G5：Option、Security ID 与调试保护

**回答：** 可解释 option 字段，但不能由型号推算板子出厂值或 Security ID。OPBT0 的只读映射为 `0xFFCD0030`，WDTA 相关字段见 F1 和 HW-E p.2884；它不是可以直接写来改变 Flash option 的普通配置寄存器。

后续使用板卡出厂配置/烧录记录和合法调试配置核对 ID、保护状态与目标器件选项。没有资料时保留未知，不填全零、全 FF 等猜测，也不建议通过整片擦除来获得“可调试”状态。

## I. Port 与 Dio

<a id="I1"></a>
### I1：LED/按键端口与极性

**回答：未知。** 用原理图网名、器件连接及 Port/Dio 配置三方核对。LED 是高/低有效、按键是否外部上拉、是否需消抖均是板级信息。参考案例用逻辑别名 `BOARD_LED/BOARD_BUTTON`，不默认绑定任意物理位，也不继承 U2A6 的映射。

<a id="I2"></a>
### I2：PMC/PFC/PFCE/PM 如何审核

**手册确认：** PM=0 输出、1 输入；GPIO 输入还需 PIBC=1；PFC/PFCE/PFCAE 组合选择复用，PMC 选择端口/复用，部分外设另由 PIPC 控制方向。先设置选择位再启用 PMC，不能同时在两个管脚启用同一互斥外设信号。来源：HW-E pp.104–109。

对于普通 Pn，ALT1～6 的选择码 `(PFCAE,PFCE,PFC)` 依次为 000、001、010、011、100、101；这只给出编码规则，具体管脚是否具有该 ALT 仍由该管脚表决定。JPORT 宽度/功能不同，不能直接套普通 Pn 写入。

**回答：** 对每个启用位登记“封装管脚→网名→功能→ALT→方向→PMC/PFC/PFCE/PFCAE/PIPC/PIBC”，再按端口聚合寄存器值并检查有效位掩码。当前 Port 配置未提供，故不能填写实际整组十六进制寄存器值。

<a id="I3"></a>
### I3：未使用引脚怎么处理

**手册确认：** 不能统一设为“输入上拉”或“输出低”。普通 GPIO 在输入端口模式且输入缓冲关闭时，部分引脚允许悬空；启用输入缓冲/特定输入复用时按表经电阻接相应电源或地。调试脚、模拟输入、专用脚有各自规定。HW-E §2.8 pp.180–186 建议所述上/下拉电阻至少 1 kΩ；模拟输入表指定各自模拟电源/地。

**回答：** 先排除当前封装不存在的位、调试/复位/电源脚、外部已驱动信号，再逐 pin 应用 §2.8。关闭输入缓冲的 GPIO 不能再被当作可读按键；未接引脚策略也不能覆盖量产测试或唤醒用途。参考案例保留逐 pin 配置，不作全端口统一清零。

<a id="J1"></a>
### J1：5.0.39 variant、内核模式与栈模型

<a id="J2"></a>

**回答：** 四个名字分别承担读时间、安排事件、查询状态、撤销事件的角色，但当前签名、Set 参数是绝对值还是延时、State 的字段、ISR 推进函数、重触发协议都应从实际生成头文件/端口指南取得。本次未确认 5.0.39 是否附带 OSTM 示例。

<a id="J4"></a>
### J4：0x2800 栈够不够

**回答：** `0x2800=10240 B=10 KiB`，只证明预留量。是否足够取决于实际栈模型、最深任务调用链、允许的 ISR 嵌套、OS/异常保存帧、FPU 上下文和库函数开销；不能按任务栈简单相加，也不能默认全体共享单栈。

建议分析“每个实际 stack object 的最坏同时占用 + 对齐/保护余量”，把启动、任务、ISR、异常分别归到对应栈；静态调用链分析结合高水位测量。测量只证明已覆盖路径，不能代替未测最坏路径。当前没有端口/应用代码，故容量结论明确为未知。
